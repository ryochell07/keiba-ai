# 設計

```
取得元 ──Provider──▶ 正規化レコード ──ingest──▶ SQLite ──features──▶ LightGBM(Plackett-Luce)
JRA HTML / 公式CSV     (providers/base.py)        (schema.sql)         │
                                                                       ▼
                     暗号化スマホページ ◀── 期待値・ランキング ◀── 全券種の同時確率 (probs.py)
```

## モジュール

| ファイル | 役割 |
|---|---|
| `http.py` | robots遵守、レート制限、再試行、取得履歴、要求数上限 |
| `providers/` | 取得元ごとの実装。追加は `Provider` を継承するだけ |
| `providers/jra_parser.py` | JRAのHTML解析。取得処理から独立 |
| `config/nar_columns.yaml` | 地方CSVのカラム定義。仕様変更時はここを直す |
| `ingest.py` | 整合性チェックとDB保存 |
| `features.py` | 特徴量。学習と予測で共通 |
| `gbm.py` | Plackett-Luce目的関数のLightGBM、位置別温度の推定 |
| `probs.py` | 全券種の確率、候補の絞り込み |
| `ev.py` | 期待値、注意フラグ、信頼度 |
| `backtest.py` | ウォークフォワード評価、手法比較 |
| `site.py` / `web/index.html` | 暗号化スマホページ |
| `registry.py` | モデルの版管理、新旧比較、ロールバック |
| `forward.py` | 発走前の予測と確定結果の照合 |
| `lab.py` / `lab_final.py` | 精度改善の実験。封鎖テストは `final` で1回だけ使える |
| `state.py` | 暗号化バックアップ |

## 主な設計判断

**JRAと地方は別モデル。** 開催体系が違うので `org` ごとに学習します。同一モデル内でも競馬場・馬場・条件を特徴量にしています。
地方の馬はIDが提供されないため、馬名と生年月日で識別します。JRAと地方の間で同一馬は名寄せしていません。ばんえい (帯広) は学習対象外です。

**確率モデル。** 上位3着までの順序をPlackett-Luce尤度で直接学習し、1→2→3着の条件付き確率で全組み合わせを列挙します。
位置別の温度 τ1〜τ3 を検証期間で推定し、下位着順ほどランダム性が増す効果を補正します。単勝確率の単純な掛け算は使いません。

**候補の絞り込み。** 18頭でも4896通りなので確率計算は全列挙です。絞り込みは保存と表示の量を抑えるためのもので、
勝率上位10頭 (`CANDIDATE_K`) に限定します。バックテストで、実際の1〜3着が候補に入る割合を確認します。

**未来情報の混入防止。**

- 当該レースの着順・タイム・上がり・通過順・確定人気・払戻・確定オッズは特徴量にしない
- 馬の履歴は `shift(1)`、騎手・調教師などの集計は前日までの累積
- オッズは `captured_at` が発走10分前以前のものだけ。確定オッズ (`captured_at='final'`) は除外
- 枠順確定前や朝の予測で欠ける項目は、学習時にも一定割合を欠損にして慣らす

`tests/test_leakage.py` がこれを検査します。意図的にリークを入れると失敗することも確認済みです。

**市場との合成。** 実データでAI単独の期待値を使うと、回収率が7割前後の見せかけのプラス候補が大量に並びました。
そこでオッズ取得後は、強さ = α×AIスコア + β×log(1/単勝オッズ) から全券種を計算します。αとβは評価期間の前半で推定し、後半だけで評価します。
地方の推定値は α=0.22、β=0.86 で、AIが市場に足せる情報はわずかです。取消馬のオッズが残るレースは市場確率が歪むので評価から除きます。

**期待値の検証の限界。** 過去の発走前オッズは中央・地方とも取得できず、最終オッズだけが手に入ります。最終オッズを見て買い目を決める検証は、
実際には不可能な判断を含むので楽観的になります。そのため `final_optimistic` と明示し、発走前スナップショットによる `cutoff` と区別します。
`cutoff` の買い目が500件以上で回収率の95%信頼区間の下限が100%を超えるまで、プラス期待値には「長期回収率は未検証」と表示します。

**モデルの更新。** 旧モデルの学習末より後の期間を前後に分け、前半まで学習した挑戦者と旧モデルを後半で比較します。
Log LossかBrierが悪化したら採用しません。回収率はばらつきが大きいので、表示はしますが採否には使いません。
合格したら全データで再学習して採用します。`keiba rollback` で戻せます。

## 無料運用の構成

GitHub Actions (公開リポジトリの標準ランナーは無料) で動かします。

| 要素 | 手段 | 超過時 |
|---|---|---|
| 定期実行 | GitHub Actions | ジョブごとに `timeout-minutes` で打ち切り |
| DBとモデルの保存 | Release asset (暗号化) | 1500MBを超えると `state pack` が停止 |
| 閲覧 | GitHub Pages (暗号化JSON) | 課金なし |
| 要求数 | 1回6000リクエストまで | 停止 |

非公開リポジトリにする場合は、Actionsが月2000分までになり、無料プランのPagesが使えません。
GitHub Actionsのスケジュール実行は遅延することがあります。発走直前のオッズを必ず取れるわけではありません。
