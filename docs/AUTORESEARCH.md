# 自動研究エージェント

Mac の Claude Code (Claude Pro のログイン) を使い、予測精度の改善を自動で繰り返す仕組みです。
成績の弱点を集計し、仮説を立て、実装して、決まった手順で精度を比べます。改善が確認できたときだけ Draft PR を作ります。

追加の固定費はかかりません。Anthropic API の従量課金は使いません (サブスクリプションのログイン以外では起動しません)。

## 1サイクルの流れ

1. 回数の上限、電源、空き容量、Claude のログインを確かめる。満たさなければ何もしない
2. main を取得し、基準 (main) を探索期間で採点して弱点を集計する (main のコミットごとに1回)
3. Claude に、弱点の集計・過去の実験 (失敗を含む)・Issue の指示を渡す
4. Claude が仮説を1つ選び、`.agent/proposal.json` に書いてから実装し、探索期間で簡易評価する (1サイクル3回まで)
5. 実行役 (`autoresearch/runner.py`) が評価し直す
   - 変更してよいファイルか
   - テスト
   - 未来情報の検査と、既存の特徴量の値が変わっていないか
   - 探索期間で合格なら確認期間
6. 結果を `~/keiba-agent/ledger.jsonl` に必ず記録する。両方の期間で改善したときだけ、枝を push して Draft PR を作る
7. Issue の指示による実験なら、その Issue に結果をコメントする

合否は Claude の報告ではなく、実行役が同じ手順でやり直した結果で決めます。

## 期間と判定

| 期間 | 範囲 | 使い方 |
|---|---|---|
| 探索 | 2025-03-01〜2025-08-31 | 仮説の探索と反復。Claude が読めるのはここまで |
| 確認 | 2025-09-01〜2026-02-28 | 探索で合格した案だけを確認する。Claude には合否だけを伝える |
| 封鎖 | 2026-03-01〜 | 使わない (`lab.LOCKED_FROM`)。開発用DBに入っていない |

期間は `lab.py` の調整用・選択用・封鎖の区分と同じです (`tests/test_autoresearch.py` で確認)。

学習は、中央が2024年、地方が2022年からです。乱数は基準と候補で同じにしています。

判定の基準:

- 主指標は Log Loss と Brier です。AI単独の確率が変わる案は AI単独で、変わらない案 (校正・合成) は市場と合成した最終確率で判定します
- 両方の期間で次を満たすと「改善」です
  - Log Loss の差の95%区間の上限が0未満 (開催日単位のブートストラップ)
  - Brier の差が負
  - AI単独で判定する案は、最終確率が有意に悪化しないこと
- 回収率は参考として表示するだけで、判定には使いません

市場の確率は、中央が確定単勝オッズ、地方が確定人気からの代用です。開発期間の地方にはオッズがないためです。
どちらも締切後の情報なので、合成の比較の基準にだけ使い、特徴量には使いません。

## 安全の仕組み

| 守ること | 仕組み |
|---|---|
| 封鎖期間を探索に使わない | 開発用DBを封鎖日より前のレースだけで作り直す。Claude 用のDBは確認期間も含まない。予測台帳・モデル・過去の実験記録は写さない |
| 未来情報を混ぜない | 既存の `tests/test_leakage.py` に加え、実データの一部で「未来のレースを消しても特徴量が変わらない」「そのレースの結果を入れ替えても変わらない」を検査する |
| 固定中の本番モデルを変えない | 既存の特徴量の列の値が変わる案は不合格にする。`freeze_models: true` と `market_only_orgs` は変えられない |
| 本番に書き込まない | エージェント専用の複製 `~/keiba-agent/repo` で作業する。本番のDB・Release・Secrets・ワークフローを扱う命令は実行役のコードにない (テストで確認) |
| main に入れない | 作るのは Draft PR だけ。マージは利用者が行う |
| Claude の権限を絞る | 通信なし、書き込みは作業コピーとキャッシュだけ、`~/keiba-ai` と `~/keiba-research` と鍵の場所は読めない、Web と MCP は使えない、確認なしで許可されない操作は拒否 (`dontAsk`) |
| 候補のコードを閉じ込める | 実行役も候補のコードは `sandbox-exec` の中で動かす (通信なし・書き込み先を限定)。プロセスの間は CSV と JSON だけで受け渡す |
| 変更の範囲 | `features.py`、`gbm.py`、`probs.py` と新しいテスト `tests/test_agent_*.py` だけ。依存パッケージは増やせない |
| 利用枠 | 1日2回、7日で8回、間隔4時間以上、1回60ターン・45分まで。利用上限に当たったら6時間止まる。電源につながっていないときは動かない |
| 同じ実験の繰り返し | 変更の指紋が同じなら評価しない。過去の実験の一覧を Claude に渡す |

Claude Code の設定は実行ごとに `runs/<実行>/claude-settings.json` に書き出します。

## 導入 (一度だけ)

1. Mac のターミナルで Claude Code にログインします。Claude Pro のアカウントを選んでください。

```bash
claude auth login
```

2. 自動研究エージェントを入れて、定期実行を登録します。

```bash
bash ~/keiba-agent/tools/scripts/autoresearch/install.sh
```

`~/keiba-agent/tools` がまだない場合は、リポジトリの `scripts/autoresearch/install.sh` を直接実行します。

1時間ごとに起動し、上限の範囲で動きます。Mac がスリープ中は動きません。

## 使い方

状況の確認:

```bash
cd ~/keiba-agent/tools && .venv/bin/python -m autoresearch.runner status
```

1サイクルをすぐ動かす (回数の上限だけ無視):

```bash
cd ~/keiba-agent/tools && .venv/bin/python -m autoresearch.runner cycle --force
```

定期実行を止める:

```bash
bash ~/keiba-agent/tools/scripts/autoresearch/uninstall.sh
```

記録の場所:

- `~/keiba-agent/ledger.jsonl`: すべての実験の仮説・条件・結果 (失敗を含む)
- `~/keiba-agent/runs/<実行>/report.md`: 実験ごとの報告
- `~/keiba-agent/runs/<実行>/change.diff`: 変更の差分
- `~/keiba-agent/logs/runner.log`: 起動の記録

## ChatGPT などからの指示 (GitHub Issues)

1. 「自動研究への指示」のテンプレートで Issue を作ります。ChatGPT の文面をそのまま貼ってかまいません
2. ラベル `agent-task` が付いた、リポジトリの所有者の Issue だけが読まれます。公開リポジトリなので、他人の Issue やコメントは無視します
3. 次のサイクルで、エージェントが指示を優先して仮説を選びます。結果はその Issue にコメントされます
4. 終わったら Issue を閉じてください

指示は研究の方向づけです。評価の手順、変更してよいファイル、権限は変えられません。

## 既存の仕組みとの関係

新しく作ったのは、評価の手順を固定する部分と、自動で回す部分だけです。学習・特徴量・確率は既存のコードをそのまま呼びます。

| 既存 | 使い方 |
|---|---|
| `features.load_frame` / `add_market` / `build_features` | 学習と採点のデータ。候補のコードの版を使う |
| `gbm.train_race_model` / `softmax_by_race` | 学習と確率。本番と同じ手順 (早期終了、検証分も含めた再学習、温度) |
| `probs.fit_blend` / `blend_strength` | 市場との合成の基準。本番と同じ |
| `lab.py` の期間 (`TUNE`、`SELECT`、`LOCKED_FROM`) と `pop_market` の考え方 | 探索・確認・封鎖の区分と、地方の市場の代用 |
| `tests/test_leakage.py` | 未来情報の検査 (候補では変更できない) |
| `freeze_models` / `market_only_orgs` | 変えない。Draft PR をマージしても固定中のモデルの予測は変わらない |

`lab.py` の各ステージは開発用DBに実験記録を書き込み、確認期間も読むため、エージェントには使わせていません。

## 限界

- 1サイクルで評価するのは1つの主催者です。乱数は1つだけなので、特徴量を足したときの差には乱数の揺れも含まれます。確認期間での再現を必須にしているのはそのためです
- 確認期間は合格した案ごとに使うので、使うほど独立性が下がります。使った回数は記録に残ります
- 本当の検証は、発走前に記録した予測による前向き評価です。Draft PR の採用は、再学習と前向き評価で確かめてから判断してください
- 研究用スナップショットは 2026-11-10 時点のもので、自動では更新しません
